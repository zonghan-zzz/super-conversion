# 页面诊断、改稿与验证

本文件是该 skill 的操作约定与方法综合，不归属于某本书的原文。

## 1. 最小输入与证据

优先复用对话已有信息：

| 输入 | 用途 | 缺失时 |
|---|---|---|
| Figma 指定节点或可读截图 | 文案、结构和位置 | 无法看页面就不能做具体诊断；先整理目标和检查计划 |
| 人群、来源、设备 | 判断信息和动作适配性 | 声明有依据的假设；影响重大时问关键问题 |
| 目标动作与最终结果 | 避免优化错误指标 | 提出候选和条件化建议；上线验证前确认 |
| 价格、权益、资质、限制 | 写真实可交付文案 | 不补造；用中性文案或明确待填字段 |
| 转化数据与研究 | 排序和验证归因 | 做启发式诊断，置信度受限 |

证据分为：**直接观察**（图中所见/实际操作）、**用户提供**（业务与数据）、**推测**（心理或因果）、**未知**（未读区域或缺数据）。记录位置及日期/版本。模糊字样不当作确定原文。

## 2. 路径与瓶颈

目标句示例：“来自行业文章的移动端访客，完成可联系的产品演示预约。”另写最终结果如“完成有效演示”，避免只看填表。

路径示例：入口承诺 → 页面抵达 → 理解适配性 → 查看证据 → 开始预约 → 提交成功 → 完成有效演示。心理环节只供诊断，不能当作已埋点事件。

手机号留资先按 [渠道与用户收益](lead-capture.md) 区分小程序与 H5；把收益承诺、实际交付及手机号用途串成同一条路径，不能套用同一张手填表。

先检查流量是否相关、业务是否可用，再诊断页面阻碍。截图中缺信息不代表整个产品没有；注明“在已提供范围内未见”。

## 3. 规则选择与优先级

页面和单个转化组件均结合 MAP 与 CY 六要素。先逐项检查互惠、承诺与兑现、信任状、畅销好评、痛点刺激、稀缺，记录证据、采用位置或不适用原因，再按下表选择主要干预。不允许仅引用福格模型完成诊断；不因六要素存在就强行添加六个模块。单按钮整改可在图外用六行短表交代，保留简洁 UI。

| 主要问题 | 首选规则 | 按需补充 |
|---|---|---|
| 流失位置不清楚 | CY-01 | BD-04 |
| 价值不明、入口与页面不匹配 | FM-02、CY-08 | BD-03 |
| 证据不足、承诺不一致 | CY-03～CY-05 | BD-03 |
| 多字段留资/操作困难 | FM-03、CY-01 | BD-05；PE-001 仅作参考 |
| 下一步不明或行动意愿弱 | FM-04、FM-02 | CY-02/03；PE-002 仅作参考 |
| 首屏价值不明、注意力分散 | FM-02、FM-04、BD-03 | BD-06；PE-003/004 仅作参考 |
| 不适合直接购买 | BD-01 | FM-05 |
| 激活后无价值体验 | BD-02 | BD-03 |
| 有真实期限/名额 | CY-07 | BD-06 |

先按理论和页面证据确定主要阻碍，再决定是否采用个人经验中的候选；不要求设计覆盖全部 PE。默认用文字解释排序：

- **P0**：已确认的关键路径阻断或严重事实错误，先修。
- **P1**：影响主要人群的重要阻碍，有证据或可快速验证。
- **P2**：次要优化、情境性建议或证据不足的探索。

另标高/中/低置信度及理由。看见某个设计事实，不代表其转化影响也有高置信度。数据充分时按受影响人数、下游价值和成本排序，无数据不输出虚构收益。

## 4. 问题卡与改后规格

关键问题使用以下字段；简单任务可合并成表：

```text
位置：Frame/node 或视觉区域；不编造节点 ID
观察：原文/结构与证据类型
阻碍假设：谁在什么时刻为什么可能无法继续
规则：主要理论规则 CY/FM/BD 及机制；必要时另列 PE 参考，不能仅凭经验断言效果
修改：可直接使用的文案、模块顺序、控件或交互状态
依赖与取舍：真实材料、业务条件、可能代价
优先级 / 置信度：理由
验证：主指标、质量指标、必要事件
```

说明保留/移动/删除/新增什么。营销页按决策需求组织；注册页以任务完成为中心；结算页不强加销售长文。

首屏先让用户理解一个核心价值和下一步，优先消除重复利益说明、同级标题和无必要的选择负担。视觉焦点、文案与 CTA 服务同一决策；详细权益、案例和行业选择按需要放在后续区域或步骤，不隐去关键条件。

视觉改动必须对应机制，例如把总价和计费周期放到提交前，减少成本不确定性。“更高级”“按钮更鲜艳”不构成完整解释。

## 5. 先分析、再建议、最后生成 UI 效果图

先完成目标、权益、核心文案、字段分步和事实检查，向用户呈现简明分析及具体建议，再调用生图能力。不要只在内部分析，也不要先生成图片再补理论解释。分析需说明“哪个用户在何处遇到什么阻碍”，建议需说明“改哪个元素、为何有效、需要什么事实支持”。福格模型诊断意愿、容易程度与提示，六要素推导说服设计，渠道能力与流程设计落实操作简化；不把两个框架机械拆成完全互斥的职责。

生成图落实已经说明的方案，不自动实现交互网页。已有任务授权内无需等待额外确认。纯方法讨论、skill 规则更新或没有实际视觉改动时可只更新规则与分析，不为展示进度重复生图。

生图提示应明确：品牌与设备、原图角色、视觉层级、需逐字保留的中文、CTA、各步字段、奖励内容、领取条件、已填写/未填写状态。多步流程可在一张设计板上并列首屏、手机号表单、成功与补全页；不必为少量修改生成整套屏幕。

生成后核查小字、字段、按钮和勾选状态，避免出现假背书、假金额、虚构倒计时或承诺。拟议奖励在图外注明待业务确认，不把它写成实际已上线权益。静态图中的动画建议只描述表现与触发方式；可编辑设计和交互实现只在用户明确要求时继续。

## 6. 验证方案

- 设计阶段检查任务理解、信息真实性、主次层级、表单恢复和设备适配。改后截图证明设计输出，不证明业务提升。
- 有条件时随机分配合格用户到对照/改版并保持分组稳定；事前确定观察窗、主指标、质量指标和停止规则。
- 明确分母与去重方式，如预约成功用户/合格访问用户；补充有效预约率、到场或成交。不混用用户与次数。
- 按基线、最小关注差异、流量和统计方法设计样本量/周期；不能统一承诺“七天即可”，也不因短期正向波动提前停止。
- 报告人数、观察期、百分点变化、相对变化及不确定性。前后比较仅作线索；多项一起改只能评估整套方案，不宣称单项贡献。
- 流量不足时先做任务观察、访谈或小规模试用；它们发现使用问题，但不能替代增长幅度的因果验证。

## 7. 交付前自查

检查 UI 图与整改方案一致、分步状态与领取承诺没有矛盾；每个关键修改有可定位证据、适用规则、具体动作和验证方式；未查看区域不作断言；价格、logo、评价、承诺、库存均有依据；模型未被写成确定因果或收益保证；工具失败不包装成已完成改稿。
